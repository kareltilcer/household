Household/Design implementation/v1 plan

Twenty-three stages to a clickable Household.

The product of this plan is one prototype that mocks the whole application — every screen in docs/design/05-screens.md, on every client, in both themes, in every state the delivery checklist names. No representative samples, no “as above”. That prototype is Household Prototype: one shell, all seventeen modules, the twelve states on a rail.

How “nothing is missing” is enforced

A ledger of this size cannot be kept honest by memory, so Stage 1 produces the instrument that keeps it honest and every later stage is measured against it.

The ledger

Every screen gets a stable id (A-14-m = inventory group A, row 14, mobile), the source line it came from, its client, its required states and its stage. It is generated from the inventory, not from my reading of it. Where the inventory names one screen twice — C-55 settings §6 Billing and A-28 Manage billing are one surface reached two ways — both ids stay and the duplicate carries an alias to the route it is reached on, so no id can read as a screen nobody built.

The state switcher

The prototype carries a developer rail with all eight switches: client, theme, density, text scale, locale, connectivity, entitlement state and screen state. Any screen’s twelve states are reachable by switching, not by building twelve copies, and the entitlement table and the three locales drive the same element tree.

The stage gate

A stage closes when every ledger row assigned to it passes the 07-delivery §3 checklist — both themes, 200 % text, colour + icon + word, 44 pt targets, absence not disabling, destructive copy that names the object. An unchecked row keeps the stage open.

One consequence worth stating now: the twelve states are switched, not drawn twelve times. That is what makes a 435-row ledger tractable without any of them being skipped — the state matrix is real and exercised, but it lives in the prototype’s plumbing rather than in three thousand static frames.

What the prototype is made of

Token layer
One file emitting primitives → semantic → component tokens as CSS custom properties, both themes on the root, dark redefining only what changes. The declared contrast pairs live here as data so they can be tested, not asserted.
Component set
The 02-components inventory, built once and reused: list row, data table, money value, sync mark, grant matrix, hold-to-complete, widget shell, reading input, and the rest. Every module screen is assembled from these; a module that needs a new component gets it added to the set, never a local copy.
Fixture household
One household with real-shaped data: Jana (owner), Petr (two modules), Adam (child, locked dashboard), Klára (none on fourteen), Miloš (tablet, Garden). Three seasons of garden history, two billing periods of readings, a ledger with a settle-up. The personas are the fixtures, so the absence pattern and the grant matrix demo themselves.
Three shells
A phone shell with the fixed five (and four) destinations and a push-and-back stack; a tablet shell with the same bar and two panes; and a web shell with the persistent sidebar. Clicking is real: routes, pushes, sheets, side panels, deep links and the wrong-household resolution all work. Not React Native Web on one side and a stretched phone on the other — three presentations of one vocabulary, as 00-brief §1 requires.
One application
All of it assembled in Household Prototype. Every screen the module files declare — all 210 of them — is collected by screens.js and reachable by clicking, rendering its own title, lede, fields, notice, actions and per-state words. Every one of them draws its own body, not its module’s: 146 of the 210 have a body written against their own module file in screenbodies.js. Of the remaining 64, forty-seven are answered per route by the four route-aware modules — Shopping, the dashboard, the account path and the platform surfaces — seven by nav and sync through surfaces.js, and ten are a module’s own root list, which is the body that screen should have. All of it reads the same HH_TASKS, HH_GARDEN and HH_ASSETS the stage artifacts are measured with, so the flow view, the tariff composer and the weekly grid are in the application rather than only in their artifact. What stays in the artifacts is the measurement — the millimetres, the fit runs, the contrast arithmetic — and every screen links to the one that measured it.

The twenty-three stages

Stages 1–6 build the vocabulary every later screen inherits and produce no demo, exactly as DS-0 does not. Resisting the pull to draw a beautiful Garden screen in week two is the plan’s main discipline.

All twenty-three stages are built and closed; each links to its own artifact below. The mobile and web count is frozen at 411 client rows over 2 995 required states, with zero rows unbuilt and zero states undrawn — the eighteen cells that kept Stages 5 and 6 open were drawn in Stage 20 and are credited to that file rather than back-dated. Scope, settled

Copy is written as if it were keys, and the second-language check is Czech — it tests both string length and the Ď Ř Ě ascenders at 200 %. Five full languages in the prototype is a different, larger piece of work.
